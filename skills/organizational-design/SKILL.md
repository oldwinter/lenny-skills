# Organizational Design

使用来自 2 位产品领导者的框架，帮助用户设计有效 organizational structures。

## 如何提供帮助

当用户请求 organizational design 相关帮助时：

1. **理解上下文** - 询问当前 structure、company stage、他们想解决什么问题，以及愿意接受哪些 trade-offs
2. **识别核心 trade-off** - 帮助他们看到 centralized（Apple-style）和 decentralized（Amazon-style）models 之间的 spectrum
3. **评估 options** - 逐一分析不同 structures 对 speed、coherence 和 cross-team dependencies 的影响
4. **指导 implementation** - 帮助他们思考如何 transition 到新 structure

## 核心原则

### 根本 trade-off：speed vs. coherence
Gustav Soderström: "On one spectrum, you have Amazon - minimize dependencies so you can run in parallel. On the other, you have Apple - centrally organized close to a single individual." Amazon 通过 autonomous teams 和最少 dependencies 优化 speed。Apple 通过 central coordination 优化 coherent user experience。两者没有绝对优劣，要根据 product 最重要的东西选择。

### Functional models 可以恢复 startup speed
Brian Chesky: "We went to a functional model. We went back to a startup." Airbnb 移除了把 leaders 与实际工作隔开的 divisional structures 和 management layers。Functional models 会集中 expertise，并减少 executives 和 ICs 之间的 "telephone game"。

### 消除不了解工作的 managers
Brian Chesky 的 restructuring 移除了不能亲自做工作的 "people managers"。Leaders 应该有足够 context 做决策，而不只是 manage reports。如果 manager 无法 review actual output，structure 就坏了。

### Structure follows strategy
正确 org structure 取决于你在优化什么。如果你需要在独立 initiatives 上快速并行执行，就 decentralize。如果你需要高度 integrated product experience，就 centralize。

## 帮助用户的问题

- "你希望通过这次 restructuring 解决什么问题？"
- "你更优化 independent teams 的 speed，还是整个 product 的 coherence？"
- "Executives 和实际做 work 的人之间有多少 layers？"
- "你的 managers 真的能 review 并理解团队 output 吗？"
- "你今天遇到的最大 coordination failures 是什么？"

## 需要提醒的常见错误

- **没有清晰问题就 reorg** - Structure changes 很 disruptive。必须清楚你在解决哪个具体问题
- **照抄另一家公司的 structure** - Amazon 的 structure 适合 Amazon 的 strategy。确保选择基于你的 needs，而不是 prestige
- **太多 management layers** - 每一层都会增加 latency 和 information loss。尽量缩短 decision-makers 与 work 之间的距离
- **Managers 不能做实际工作** - 如果 leaders 不理解 output，就无法做出好决策
